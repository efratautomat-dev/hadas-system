# 09 — אפליקציית האנדרואיד

> האפליקציה שהטאבלטים בחנות מתקינים. **APK אחד גנרי לכל הלקוחות**, בהפצה ישירה
> (sideload) ולא דרך חנות. נבנה 08.09.2026 בענף `feature/android-app`.
> ההחלטות והנימוקים המלאים: `~/ymux-drops/incontrol-android-build-spec.md`.

---

## 1. מה זה, בשורה אחת

**מעטפת דקה שטוענת את האתר החי.** ה-APK אינו מכיל את המערכת — הוא מכיל דף אחד
(`shell/`) שתפקידו לענות על שאלה אחת: *לאיזו לקוחה שייך הטאבלט הזה.* אחר כך
Capacitor טוען את האתר של אותה לקוחה, וכל השאר זהה לחלוטין למה שרץ בדפדפן.

**המשמעות התפעולית:** `npm run deploy` הרגיל מעדכן גם את הטאבלטים. בניית APK
נדרשת רק כשמשתנה **המעטפת עצמה** — מסך הקוד, מסך אין-חיבור, האייקון, ההרשאות או
גרסת Capacitor.

**המחיר, במפורש:** פריסה שבורה שוברת את הטאבלט מיידית. אין חבילה מקומית ליפול
אליה. בגלל זה קיים ה-watchdog (§4).

```
APK גנרי ─┬─ shell/ (מקומי)  → מסך קוד חנות · מסך אין חיבור
          │      ↓ קוד → כתובת (public/app/stores.json)
          └─ אתר הלקוחה החי  → כל המערכת
```

## 2. הדבר הכי חשוב בקובץ הזה: הגשר מוזרק לכתובת אחת

```java
// Bridge.java:266 — קוד המקור של Capacitor
String allowedOrigin = Uri.parse(appUrl)...
WebViewCompat.addDocumentStartJavaScript(webView, injector.getScriptString(),
                                         Collections.singleton(allowedOrigin));
```

Capacitor מזריק את הגשר הנייטיבי ל־**origin אחד בלבד**, שנקבע כשהאפליקציה עולה.
לכן **ניווט** לאתר הלקוחה אחרי העלייה מגיע לדף בלי גשר: אין הדפסה, אין כפתור
אחורי, אין הורדות, אין החלפת חנות — והכל נכשל בשקט.

**התיקון:** `MainActivity.onCreate` קורא את הכתובת השמורה מ-SharedPreferences
(`CapacitorStorage`, המפתח `incontrol.storeUrl`) ובונה ממנה `CapConfig` **לפני**
`super.onCreate`. הזנת קוד חנות שומרת את הכתובת וקוראת ל-`StoreGate.restart()`,
שמחזיר את האקטיביטי דרך `onCreate` — לא ניווט.

⚠️ **קונפיג תוכניתי מחליף את `capacitor.config.json` במלואו.** כל מה שמוגדר
ב-`capacitor.config.ts` (androidScheme, errorPath, allowNavigation) חייב להופיע גם
ב-`MainActivity`. שתי הגדרות בשני מקומות שהן הגדרה אחת.

## 3. קוד חנות ורג'יסטרי

| | |
|---|---|
| איפה נשמר | אחסון **נייטיבי** (Preferences), לא localStorage |
| למה נייטיבי | המעטפת ואתר הלקוחה הם שני origin — רק אחסון נייטיבי נגיש לשניהם, וכך "החלפת חנות" באתר יכולה לאפס קוד שנשמר במעטפת |
| הרשימה | `public/app/stores.json` → מוגש מ-`https://incontrol.ctrlplusf.com/app/stores.json` |
| גיבוי | עותק מוטבע ב-APK (`shell/stores.json`) לאתחול ראשון ברשת חלשה |
| לקוחה חדשה | שורה בקובץ. **בלי בנייה מחדש ובלי לגעת באף טאבלט** |

הרשימה נקראת מחדש בכל הפעלה, ולכן שינוי כתובת של לקוחה מגיע לטאבלטים מיד.

⚠️ nginx של הדמו חייב להגיש אותה עם `Access-Control-Allow-Origin: *` — המעטפת
קוראת אותה מ-origin מקומי. בלי זה הדפדפן חוסם, והמעטפת נופלת לעותק המוטבע.

## 4. שלוש דרכי מוצא — בכוונה

בחנות עם עשרה טאבלטים, מסך שאי אפשר לצאת ממנו הוא קריאת שירות.

1. **הגדרות → העדפות → "החלפת חנות"** — המסלול הרגיל. מוצג רק כש-`isNative()`.
2. **watchdog של 25 שניות** — `MainActivity` ממתין לקריאת `StoreGate.alive()`
   ש-`initNative()` שולח כשהמערכת עולה. לא הגיעה → הכתובת נמחקת והאפליקציה חוזרת
   למסך הקוד עם הודעה. זה מכסה את מה ש-`errorPath` **לא** מכסה: אתר שנטען ואז קרס
   נראה כמסך לבן, לא כשגיאת רשת.
3. **הגדרות → אפליקציות → InControl → אחסון → נקה נתונים** — מוצא אחרון.

ה-watchdog מוחק גם את הקוד וגם את הכתובת — אחרת מסך הקוד היה פותר את אותו קוד
לאותה כתובת שבורה, והטאבלט היה נכנס ללולאה.

## 5. מה WebView לא עושה, ואיפה זה מטופל

הכל עובר דרך מודול אחד: **`src/lib/native.ts`**. אין בו אף `import` סטטי של
`@capacitor/*` — הפלאגינים נטענים ב-`import()` עצל בתוך ענף `isNative()`, ולכן
חבילת הדפדפן והדמו לא משתנות.

| מה שבור ב-WebView | הפתרון | קוראים |
|---|---|---|
| `window.print()` הוא no-op, `window.open('','_blank')` מחזיר null | `printHtml()` → `print.html` בדומיין של האתר, המסמך דחוס ב-**fragment** של הכתובת | `pdfConfig.openPrintWindow` (כל ההדפסות) |
| אין מנוע PDF | כפתור "פתיחת המסמך" → כרום. **סריקות תמונה נשארות בפנים** | `PdfPreviewModal.DocumentBody` |
| `download` על `blob:` מתעלם | `saveOrShareFile()` → Filesystem + תפריט שיתוף | `Payments`, `Settings` |
| טאב חדש לא קיים | `openExternal()` → ACTION_VIEW לכרום האמיתי | `storage.ts`, `Alerts` |

**למה fragment ולא Storage:** הפרגמנט לא נשלח לשרת אף פעם, ולכן נתוני הספקים לא
עוזבים את המכשיר; אין bucket חדש, אין מדיניות, ואין קבצי זבל לניקוי. `data:`
ו-`blob:` נבדקו ונפסלו — כרום חוסם ניווט עליון ל-`data:` מאז גרסה 60, ו-blob שייך
לתהליך שיצר אותו. יש שמירת גודל של ~200KB מקודדים עם הודעה בעברית.

**כפתור אחורי:** `Layout` ו-`EmployeeDashboard` כבר משקפים את מצבם ל-`history`,
ולכן המאזין רק קורא `history.back()`. **אפס שינויים בשני הקבצים.** ב-root הוא
ממזער ולא סוגר. ⚠️ מודאלים אינם ב-stack ההיסטוריה — "אחורי" עם מודאל פתוח ינווט
את הדף שמאחוריו.

## 6. תאימות WebView

הבילד היה דורש **כרום 93**; טאבלט אנדרואיד 10 עם WebView ישן הציג **מסך לבן** —
גם בדפדפן וגם באפליקציה. `vite.config.ts` מקמפל ל-`chrome73`, ו-`index.html` נושא
polyfill יחיד ל-`Object.hasOwn` (ה-API היחיד בכל המערכת שחרג).

**לפני שמעלים את היעד:** לסרוק את הבילד בפועל, לא לנחש. מסך לבן ב-WebView הוא
תמיד החשוד הזה, והוא לא מייצר שום הודעת שגיאה שמישהו רואה.

## 7. בנייה, חתימה והפצה

```bash
npm run build:apk              # APK חתום + העלאה אוטומטית לקישור הקבוע
npm run build:apk -- --debug   # בדיקה מהירה על מכשיר, בלי חתימה
npm run build:aab              # Play Store — שלב 2, לא בשימוש
npm run sync:android           # רק סנכרון המעטפת לפרויקט האנדרואיד
```

**סביבה:** JDK 21 (Capacitor 8) ו-Android SDK 36 ב-`/home/runner/android-sdk`.
`ANDROID_HOME` נקבע בתוך הסקריפט, לא ב-shell profile.

**חתימה:** `android/incontrol-release.keystore` + `android/key.properties` —
**שניהם מחוץ ל-git**. ⚠️ אובדן ה-keystore = אי אפשר לעדכן לעולם טאבלט שכבר
מותקן; אנדרואיד דוחה עדכון בחתימה שונה. גיבוי אצל הבעלים.

**קישור ההפצה — קבוע, ולא משתנה לעולם:**

```
https://<project>.supabase.co/storage/v1/object/public/app-releases/incontrol.apk
```

⚠️ **מלכודת שתפסה אותנו פעמיים ביום אחד:** `npm run deploy:demo` מסנכרן את הבילד
לתיקיית הדמו **ומוחק כל מה שאינו בו**. כך נעלמו גם רשימת החנויות וגם ה-APK באמצע
בדיקות. לכן: הרשימה חיה ב-`public/` (ונכללת בכל בילד), וה-APK חי ב-Supabase
Storage (מחוץ לטווח הפגיעה). **אל תניחו קובץ תפעולי בתיקיית הדמו.**

nginx של הדמו מגיש `.apk` עם `application/vnd.android.package-archive`. עם
`application/octet-stream` אנדרואיד מוריד קובץ ואז אומר "לא ניתן לפתוח".

## 8. התקנה אצל הלקוחה

1. לפתוח את הקישור **בכרום של הטאבלט**.
2. "הורד בכל זאת" (אזהרה סטנדרטית לכל APK מחוץ לחנות).
3. ללחוץ על הקובץ → **פעם ראשונה בלבד**: "אפשר מהמקור הזה" → חזרה → התקן.
4. להקליד את קוד החנות. פעם אחת לכל טאבלט.

**חסמים שנתקלנו בהם בפועל:**

| תסמין | סיבה |
|---|---|
| ההתקנה לא מתחילה, בלי שגיאה | **חוסם אוטומטי** של סמסונג (אבטחה ופרטיות) |
| אותו דבר, במכשיר מנוהל | **סינון סייפטק** — חוסם התקנה מחוץ לרשימה מאושרת. דורש אישור מהם, או מעבר ל-Play Store |
| "לא ניתן לפתוח את הקובץ" | סוג MIME שגוי בשרת (§7) |
| ההרשאה ניתנה ועדיין נכשל | ההרשאה היא **לפי אפליקציה** — לאשר לזו שפותחת את הקובץ |

עדכון = התקנה מעל הקיימת. הנתונים והקוד נשמרים, כל עוד אותו keystore.

## 9. בנייה ממותגת ללקוחה

```bash
npm run build:apk                      # גנרי: מסך קוד חנות, APK אחד לכולם
npm run build:apk -- --client=hadas    # הדס: האייקון שלה, השם שלה, הכתובת צרובה
```

**לקוחה חדשה = קובץ אחד.** `clients/<code>.json` מחזיק כתובת, `applicationId`, שם,
נתיבי אייקון ומונה גרסה. שלושה קובצי אייקון ב-`clients/<code>/` (1024×1024:
`icon-only`, `icon-foreground`, `icon-background`). אין שינוי קוד.

| | גנרי | ממותג |
|---|---|---|
| מסך קוד חנות | יש | **אין** — הכתובת צרובה |
| אייקון ושם | InControl | של הלקוחה |
| `applicationId` | `com.ctrlplusf.incontrol` | `...incontrol.<code>` |
| קובץ ההפצה | `app-releases/incontrol.apk` | `app-releases/<code>.apk` |
| מניפסט גרסה | `app-version.json` | `app-version.<code>.json` |
| מונה גרסה | ב-`build.gradle` | **בקובץ הלקוחה** — סדרה נפרדת לכל אחת |

### ⚠️ ה-`applicationId` הוא עניין של ציות, לא של שמות

`applicationId` שונה פירושו **אפליקציה אחרת לגמרי** — גם לאנדרואיד וגם לכל מסנן
ניהול מכשירים. אצל הדס זה קונקרטי: **סייפטק אישרו את `com.ctrlplusf.incontrol`,
והאישור חל על מזהה החבילה** — כלומר כל גרסה עתידית באותו מזהה ובאותה חתימה נכנסת
מעצמה, בלי לחזור אליהם. לכן הבנייה הממותגת של הדס **שומרת על המזהה המאושר**
ומוותרת על סיומת.

מה שנגזר מזה:

- **לעולם לא לשנות `applicationId` של לקוחה חיה.** שינוי = אפליקציה חדשה, אישור
  חדש, והתקנה **לצד** הקיימת במקום מעליה.
- `versionCode` חייב לטפס מעל מה שכבר מותקן, אחרת אנדרואיד מסרב לעדכן.
- **לקוחה חדשה שמסוננת בסייפטק תזדקק לאישור נפרד למזהה שלה** — שלב בהקמה, לא
  בבנייה.
- המיתוג עצמו (אייקון, שם, כתובת) **אינו דורש מזהה נפרד**. הוא נדרש רק אם צריך
  שתי לקוחות על אותו מכשיר — מצב שלא קיים בפועל.

הסיומת, כשהיא קיימת, היא גם איך האפליקציה יודעת לאיזה מניפסט גרסה לפנות: היא
קוראת את ה-`applicationId` של עצמה. בלי סיומת היא קוראת את `app-version.json`
מהאתר של הלקוחה — שהוא ממילא שלה בלבד.

⚠️ **המלכודת שעלתה בבנייה הראשונה:** `npx cap sync` **כותב מחדש את
`res/values/strings.xml`** מתוך `capacitor.config.ts`. לכן הזהות מוזרמת דרך
`INCONTROL_APP_ID` / `INCONTROL_APP_NAME` שהקונפיג קורא — ולא נכתבת לקובץ אחרי
הסנכרון. כתיבה ידנית אחרי sync נראית עובדת, ומייצרת APK "ממותג" שכולו גנרי,
בלי שום שגיאה.

⚠️ **שחזור הזהות נעשה מ-git** (`git checkout --`), לא מצילום מצב בתחילת הריצה:
בנייה שקרסה אחרי המיתוג משאירה קבצים ממותגים, והריצה הבאה הייתה "משחזרת" אותם
בנאמנות. git הוא העותק היחיד שהוא בוודאות הזהות הגנרית.

**הפאנל שיחליף את הטרמינל:** `spec/13-ADMIN-PANEL.md`.

## 10. מה עדיין פתוח

- **מודאלים וכפתור אחורי** (§5) — ייראה ביום הראשון.
- **יעדי מגע < 32px** — 43 במסך חשבוניות, 21 בהתראות, 17 בהתאמת כרטסות.
- **תבנית המייל ב-Supabase** — חייבת לכלול `{{ .Token }}` כדי שקוד הכניסה יישלח.
  מגבלת ה-SMTP המובנית נמוכה מאוד ועלולה לחנוק מסך התחברות.
- **המצלמה בתוך WebView** — עובדת דרך `<input type="file">` של Capacitor, טרם
  נבדקה על טאבלט החנות.
- **Play Store (שלב 2)** — `build:aab` כבר קיים. הופך להכרח אם סייפטק חוסמת.
- ⚠️ **שתי בדיקות ה-E2E בריפו נכשלות — וגם על `main` בלי האפליקציה.**
  `demo-walkthrough` ו-`marketing-walkthrough`, שתיהן על
  `expect(locator).toBeVisible()`. הן נשברו כשהמסכים השתנו והסלקטורים לא עודכנו,
  ולכן **אין כרגע רשת ביטחון אוטומטית** לאף שינוי — לא רק לאפליקציה. פריט נפרד,
  לא חלק מעבודת האנדרואיד.
