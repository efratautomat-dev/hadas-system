# 08 — מערכת ההדגמה (incontrol.ctrlplusf.com)

> המסמך המרכז של כל מה שקשור למערכת ההדגמה: מה היא, איפה היא רצה, איך מעדכנים אותה,
> ולמה היא לא יכולה לגעת במערכת האמיתית. אם משהו כאן סותר מסמך אחר — **המסמך הזה קובע**
> לגבי ההדגמה, ו‑[01-ARCHITECTURE](./01-ARCHITECTURE.md) §3 קובע לגבי הפרודקשן.

## 1. מה זו מערכת ההדגמה

עותק חי ומלא של מערכת הדס, פתוח בכתובת ציבורית, שרץ על **נתונים בדיוניים לחלוטין**
ואינו מחובר לשום בסיס נתונים. נועד להראות את המערכת ללקוחות פוטנציאליים, לשותפים
ולמשקיעים בלי לחשוף ולו שורה אחת של מידע עסקי אמיתי.

| | |
|---|---|
| **כתובת** | https://incontrol.ctrlplusf.com |
| **סיסמאות** | שלוש — אחת לכל מסלול מוצר. ראו §5א |
| **שם המערכת** | **incontrol** — לא "הדס". ראו §3א |
| **תפקידים** | מנהלת (המערכת המלאה) / עובדת (המסך המצומצם) — נבחר בכניסה, ניתן להחלפה בכל רגע |
| **נתונים** | `demo-seed.json` — 10 ספקים, 40 חשבוניות, 8 תשלומים, 2 חזרות, 4 כרטסות, 6 התראות |
| **כתיבה** | נקלטת בממשק ונעלמת ברענון — **חוץ מהלוגו**, שנשמר לאורך הסשן. ראו §4א |

הכל בדיוני: השמות, הח״פים, הסכומים והמסמכים. `demo-seed.json` פותח בהצהרה מפורשת
על כך (`_meta.note`).

## 2. איך זה בנוי

```
   דפדפן  ──HTTPS──►  Cloudflare  ──►  Traefik (coolify-proxy)  ──►  hadas-demo-web-1
                       (פרוקסי)         :80 / :443 על השרת            nginx:alpine
                                                                            │
                                                         bind mount ────────┘
                                                    /home/runner/hadas-demo/html
                                                              ▲
                                                              │ rsync
                                                    npm run deploy:demo
                                                              ▲
                                                              │ vite build --mode demo
                                                    ~/hadas-system  (אותו ריפו)
```

**קבצים סטטיים בלבד.** אין Node שרץ, אין API, אין בסיס נתונים. כל הנתונים נצרבים
לתוך קובץ ה‑JavaScript בזמן הבנייה, ומשם הם נטענים לזיכרון הדפדפן.

### השרת

| | |
|---|---|
| **ספק** | Contabo |
| **מארח** | `vmi3374342.contaboserver.net` |
| **IP** | `173.249.25.110` |
| **מערכת** | Ubuntu 24.04 LTS |
| **משתמש** | `runner` (עם sudo) |

השרת **כבר** מריץ [Coolify](https://coolify.io) עם **Traefik** כ‑reverse proxy, ועליו
יושבים אתרים נוספים (`bnokod`, `demo-tova`, `nofshimrekhasim`, `portfolio-site`).

> ⚠️ **אין להתקין Nginx או Apache על השרת עצמו.** פורטים 80 ו‑443 שייכים ל‑Traefik.
> התקנה של שרת ווב נוסף תפיל את כל האתרים האחרים. ההדגמה רצה **בתוך** קונטיינר
> מאחורי אותו Traefik, בדיוק כמו שאר האתרים.

### קבצי ההרצה — `/home/runner/hadas-demo/`

```
hadas-demo/
├── docker-compose.yml    שירות nginx:alpine + תוויות Traefik
├── nginx.conf            הגשה סטטית: מטמון, robots, SPA fallback
└── html/                 ← תוצר הבנייה. נכתב על ידי הפריסה, לא ידנית
```

התיקייה הזו **אינה חלק מהריפו** — היא תצורת הרצה של השרת. אם היא נמחקת, אפשר לשחזר
אותה מהסעיף הזה ולהריץ `npm run deploy:demo`.

### DNS ו‑SSL — כבר מוגדרים, אין מה לעשות

`ctrlplusf.com` מנוהל ב‑Cloudflare ו‑`incontrol` כבר מצביע לשרת דרך הפרוקסי
(הענן הכתום). התעודה מונפקת אוטומטית על ידי **Traefik מול Let's Encrypt** (אתגר
HTTP-01) ומתחדשת לבדה כל 90 יום. **אין certbot ואין תעודה ידנית לתחזק.**

## 3. הדגל שמפעיל את ההדגמה — ולמה יש נעילה

`src/lib/demo.ts` הוא הקובץ היחיד שמחליט אם המערכת רצה על נתוני דמו. יש שני מצבים:

| מצב | מה מפעיל | איפה | סיסמה |
|---|---|---|---|
| **מקומי** | `?demo=1` או `VITE_DEMO_MODE=true` | שרת הפיתוח בלבד | אין |
| **עצמאי** | `VITE_DEMO_STANDALONE=true` בזמן הבנייה | הבילד הציבורי | יש |

הנעילה: `import.meta.env.PROD` אמת בכל `vite build`, ולכן המצב המקומי **לא יכול**
להידלק בפרודקשן — לא דרך משתנה סביבה ולא דרך פרמטר ב‑URL. הדבר היחיד שפותח בילד
פרודקשן הוא `VITE_DEMO_STANDALONE`, משתנה שקיים אך ורק ב‑`.env.demo`.

> 🚫 **אסור להוסיף `VITE_DEMO_STANDALONE` לפרויקט בוורסל.** זה המתג היחיד שיגרום
> למערכת האמיתית של העסק להציג נתונים בדיוניים במקום חשבוניות אמיתיות.

**בדיקה שהנעילה עובדת** — הבילד הרגיל לא מכיל אפילו את קוד ההדגמה:

```bash
npm run build
grep -c "INCONTROL2026\|כניסה להדגמה" dist/assets/*.js   # חייב להחזיר 0
```

## 3א. המיתוג — שם המערכת מול שם המשתמשת

ההדגמה נושאת שם משלה: **incontrol**. היא מציגה את המוצר, לא את העסק שמשתמש בו,
ולכן היא לא נקראת "הדס".

`src/brand.config.ts` נשאר מקור האמת היחיד לפלטה ולברירות המחדל, ומאפשר לבילד לדרוס
**חמש מחרוזות בלבד** דרך משתני סביבה. הצבעים אינם ניתנים לדריסה בכוונה: בילד שרוצה
פלטה אחרת הוא לקוח אחר, וזה מה שעריכת הקובץ עצמו נועדה לו.

| משתנה | ב‑`.env.demo` | מה זה |
|---|---|---|
| `VITE_BRAND_NAME` | `incontrol` | שם המערכת — סרגל צד, מסך כניסה, כותרות |
| `VITE_BRAND_TAB_TITLE` | `incontrol` | כותרת הלשונית בדפדפן |
| `VITE_BRAND_GREETING` | `אורח` | **למי** הדשבורד אומר שלום |
| `VITE_BRAND_LOGO` | `/incontrol-logo.svg` | לוגו ברירת המחדל |
| `VITE_BRAND_FAVICON` | `/incontrol-logo.svg` | אייקון הלשונית |

**הלוגו חייב היה להשתנות, לא רק השם.** `/logo.png` הוא ה‑wordmark של הדס — המילה
"Hadas" כתובה בתוך התמונה — ולכן הדגמה שנקראת incontrol ומציגה אותו סותרת את עצמה
במבט ראשון. `public/incontrol-logo.svg` הוא מארק ייעודי (מד/חוגה, לא מסמך: ההבטחה
היא שליטה במה שכבר מגיע, לא תיוק ניירת).

הוא מצויר לשני המקומות שבהם האפליקציה שמה לוגו, ולהם רקעים הפוכים: משבצת 28px
בסרגל הצד על ורוד כמעט־לבן, ומשבצת 40px על אריח בורדו במסך הכניסה. גליף שטוח אחד
לא יכול לשרת את שניהם, ולכן המארק נושא **צלחת בורדו משלו עם גליף לבן**: על הקופסה
הבהירה הצלחת היא המארק, ועל האריח הבורדו הצלחת נבלעת והגליף הלבן נושא אותו.

**אייקון הלשונית:** `index.html` מחזיק `<link rel="icon">` קשיח אחד ומשותף לכל
הבילדים, אז `applyBrand` דורס אותו בזמן ריצה (כולל ה‑`type`, כי הדריסה עשויה להיות
SVG). בפרודקשן הערך זהה לזה שבקובץ, כלומר שום דבר לא השתנה שם.

**כשיהיה לוגו incontrol אמיתי** — מחליפים את שני הנתיבים ב‑`.env.demo` ומריצים
`npm run deploy:demo`. שום דבר אחר לא צריך להשתנות.

**ההפרדה בין `appName` ל‑`greetingName` היא העיקר.** קודם הדשבורד בנה את הברכה משם
המערכת, מה שעבד רק במקרה — אצל הדס שם המוצר ושם הבעלים זהים. ברגע שהמוצר קיבל שם
משלו זה היה נשבר ל"בוקר טוב incontrol", כאילו המערכת מברכת את עצמה. עכשיו יש שני
שדות: **המוצר** ו**האדם שיושב מולו**. בהדגמה ציבורית האדם הזה הוא `אורח`.

בפרודקשן שני השדות הם `הדס`, ואף אחד מהמשתנים אינו מוגדר בוורסל — כלומר התנהגות
המערכת האמיתית לא השתנתה כלל.

## 4. שער הכניסה — סיסמה ובורר תפקיד

הכניסה להדגמה עוברת דרך `src/components/DemoGate.tsx`: סיסמה, ובחירה אם להיכנס
בתור **מנהלת** או **עובדת**. הסיסמה שהוקלדה קובעת גם את **מסלול המוצר** שייפתח (§5א). הבחירה נשמרת ב‑`sessionStorage`, וכפתור צף
(`DemoRoleSwitcher.tsx`) מאפשר להחליף תפקיד בכל רגע בלי להקליד סיסמה שוב.

איך זה מנתב בלי לגעת בקוד האמיתי: `useAuth` שואל את הטבלה `allowed_users` מה התפקיד
של המשתמש. הלקוח המדומה (`demoClient.ts`) מגיש את הטבלה הזו **חיה** מתוך
`demoGate.getDemoRole()` במקום מהזרע הסטטי. `useAuth`, `ProtectedRoute` והמסכים
עצמם לא יודעים שיש הדגמה בכלל.

### ⚠️ הסיסמה הזו אינה אבטחה

הסיסמה נמצאת בתוך ה‑JavaScript שנשלח לכל מבקר. מי שפותח את כלי המפתחים בדפדפן
יראה אותה. **זהו פעמון, לא מנעול.**

זה מקובל כאן מסיבה אחת: **אין שום דבר מאחורי הדלת**. לבילד ההדגמה אין מפתחות
Supabase, אין מפתח API ואין נתיב רשת לשום מערכת אמיתית. התרחיש הגרוע ביותר של
סיסמה שדלפה הוא שמישהו יראה את אותה הדגמה שאנחנו מחלקים בכוונה.

**כשתידרש הגנה אמיתית** (הצגה פרטית ללקוח מסוים, משהו שצריך להיות מבוקר) — התשובה
אינה לסבך את הקוד. הצפנה של סיסמה בצד הלקוח לא קונה כלום. שמים את ההגנה לפני
הקונטיינר, בלי שינוי קוד:

- **Cloudflare Access** — חינם עד 50 משתמשים, אימות במייל, רשימת מורשים, לוג כניסות.
  מוגדר לגמרי בפאנל של Cloudflare.
- **Basic Auth ב‑Traefik** — תווית אחת נוספת ב‑`docker-compose.yml` של ההדגמה.

## 4א. החלפת הלוגו מתוך המערכת — עובדת, ויש זיכרון

**איפה:** הגדרות ← לשונית **העדפות** ← "לוגו המערכת" (ולא בלשונית פרופיל, ששם כל
הפאנלים מוסתרים מאחורי `SHOW_LEGACY=false` — גם בפרודקשן).

**מה קורה בהדגמה:** הקובץ נקרא לתוך `data:` URL ונשמר, יחד עם רשומת
`app_settings.app_logo_url`, ב‑`sessionStorage`:

- הלוגו מתחלף מיד בסרגל הצד ובכל מקום שקורא `useAppLogo`
- הוא **שורד רענון דף**, כך שאפשר להעלות לוגו של לקוח ולהמשיך לטייל במערכת
- הוא **מת עם סגירת הלשונית** — המבקר הבא מקבל את ההדגמה הנקייה בחזרה
- הכפתור הקיים "איפוס ללוגו ברירת מחדל" מנקה אותו, בלי טיפול מיוחד

**למה זה נבנה:** קודם הפעולה הזו נכנסה ל‑stub הגנרי — האחסון קיבל את הקובץ, ה‑upsert
חזר בלי שגיאה, והמסך הכריז "הלוגו עודכן בהצלחה ✓" **בזמן ששום דבר לא השתנה**. הדגמה
שמדווחת על הצלחה שלא קרתה גרועה מהדגמה בלי הכפתור, במיוחד כשמי שצופה הוא לקוח
פוטנציאלי שמסתכל על המותג שלו.

**הכלל שנוצר מזה:** בהדגמה, `app_settings` היא הטבלה היחידה שהכתיבה אליה **אמיתית**
(`src/lib/demoSettings.ts`). כל השאר נשאר no-op בכוונה, כדי שסיפור ההדגמה יתחיל תמיד
מאותו מקום. סף האישור בהגדרות נשמר גם הוא לאורך הסשן — הסיפור המוזרע לא נפגע, כי
`awaiting_approval` נקבע לכל חשבונית בנפרד ולא נגזר מהמספר הזה.

> ⚠️ הלוגו **אינו** מוחלף בקבצי ה‑PDF: `src/utils/pdf/pdfConfig.ts` בונה נתיב מוחלט
> מ‑`brand.logoPath` ולא קורא את `app_settings`. זו התנהגות קיימת של המערכת, לא של
> ההדגמה.

## 5א. שלושת מסלולי המוצר

המערכת נמכרת בשלוש רמות, וכל מתעניין רואה רק את זו שמתאימה לו. **הסיסמה שאת
שולחת היא שקובעת מה הוא רואה.**

| מסלול | סיסמה | מה נכלל |
|---|---|---|
| **בסיסי** | `INCONTROL-BASIC` | דשבורד · צילום מסמך · התראות · ספקים · חשבוניות · הגדרות |
| **מתקדם** | `INCONTROL-PRO` | + כרטסת ספק · תשלומים · תעודות משלוח · חזרות · **התאמת כרטסות** |
| **מותאם** | `INCONTROL2026` | + אינטגרציות · לוגי מערכת · ייצוא לביזיבוקס |

**אין בורר מסלול בממשק, וזה מכוון.** מתעניין שיכול לבחור יבחר תמיד את העליון, וזה
בדיוק ההפך מהמטרה. בורר התפקיד (מנהלת/עובדת) כן נשאר — הוא משחק **בתוך** המסלול.

### למה התאמת כרטסות במסלול 2 ולא 3

זה הפיצ'ר שמוכר את המערכת. אם הוא נעול ברמה היקרה, רוב המתעניינים לא רואים את
הסיבה לקנות — ואי אפשר למכור איתו את הרמה האמצעית. הוא גם כבר בנוי ולא עולה כלום
לספק. **מה שעולה זמן אצל כל לקוח בנפרד — חיבור קופה והתאמות — הוא מה שראוי למחיר
העליון.** לכן מסלול 3 מוכר הסתגלות, לא מסכים.

### ההגדרה — `src/lib/tiers.ts`

מקור אמת יחיד. המסלולים **מצטברים במבנה** (כל רמה פורשת את זו שמתחתיה במקום לחזור
עליה), כך שפיצ'ר לא יכול ליפול מרמה גבוהה בטעות עריכה. להזיז פיצ'ר בין רמות = שורה
אחת בקובץ הזה, ותו לא.

**זה לא מושג של הדמו.** אותה קטלוג הוא מה שהרשאה אמיתית לפי לקוח תקרא בבוא היום;
עד אז `currentTier()` מחזיר `custom` מחוץ לדמו, כלומר **המערכת החיה ממשיכה להראות
בדיוק מה שהראתה**. גם הדמו המקומי (`?demo=1`) והרצת Playwright ממשיכים לראות הכל,
כי אין להם דלת שקובעת מסלול.

### מה חייב להיסגר יחד עם המסך

הסתרת פריט מהתפריט **לא מספיקה**. כל מקום שמצביע על מסך חסום מפרסם פיצ'ר שאי אפשר
לפתוח. בפועל נמצאו וטופלו:

- **קוביות הדשבורד** — "תשלומים החודש", "חזרות פתוחות"
- **הבאנרים** — "אי‑התאמות בכרטסות ספקים"
- **פאנלים שלמים** — "תשלומים קרובים", "תעודות משלוח"
- **התראות** — מסוננות ב‑`useAlerts` עצמו, מקור אחד שממנו יורשים הדשבורד, מסך
  ההתראות, המונים והתג בסרגל. סוג התראה שאינו במיפוי **נשאר גלוי** — להסתיר אזהרה
  שלא הצלחנו לסווג זו הטעות הגרועה מבין השתיים
- **לשונית ייצוא לביזיבוקס** בהגדרות, ו**כרטיסי מסך העובדת**
- **ניווט דרך היסטוריה** — `Layout` מחזיר לדשבורד אם העמוד מחוץ למסלול

**כשמוסיפים מסך חדש** — להוסיף אותו לרמה המתאימה ב‑`tiers.ts`, ולבדוק מי עוד מצביע
עליו.

### מסך האינטגרציות

`src/components/Integrations.tsx` — נקודות החיבור שמסלול 3 מוכר. כל שורה אומרת
במפורש אם היא **קיימת במערכת** (מייל, Drive, ייצוא להנהלת חשבונות) או **בהתאמה
אישית** (חיבור קופה, מערכות נוספות). הפרדה הזו היא העיקר: דמו שמרמז שחיבור קופה כבר
בנוי הוא הבטחה שאיש לא התכוון לתת.

המסך **קיים רק בדמו** — במערכת שלקוח כבר קנה, אינטגרציה או מוגדרת או לא, ודף
שמפרט מה אפשר לקנות לא שייך לכלי עצמו.

## 5. פריסה — הכלל שאסור לשבור

**למערכת שני יעדי פריסה, וכל שינוי חייב להגיע לשניהם:**

| יעד | מה זה | איך מגיע לשם |
|---|---|---|
| **ורסל** | המערכת האמיתית שהעסק עובד עליה | דחיפה ל‑`main` → ורסל בונה לבד |
| **הדגמה** | `incontrol.ctrlplusf.com` | בנייה + סנכרון על השרת הזה |

פריסה ליעד אחד בלבד יוצרת אחת משתי תקלות: הדגמה שמראה מערכת שכבר לא קיימת, או עסק
שרץ על קוד שאי אפשר להדגים. הסקריפט `scripts/deploy.mjs` קיים כדי שזה לא יקרה.

```bash
npm run deploy                    # שני היעדים — זו ברירת המחדל, השתמשי בה
npm run deploy:demo               # ההדגמה בלבד
npm run deploy:vercel             # דחיפה לוורסל בלבד
npm run deploy -- --dry-run       # להראות מה יקרה, בלי לפרוס
npm run deploy -- --allow-dirty   # לעקוף את דרישת עץ ה-git הנקי
```

מה `npm run deploy` עושה, לפי הסדר:

1. **שער** — בודק שעץ ה‑git נקי ושתאומי הקוד (`check-twins`) לא נפרדו.
2. **ורסל** — `git push origin <ענף>`. אם הענף אינו `main`, הסקריפט **אומר במפורש**
   שהפרודקשן עוד לא התעדכן ושצריך מיזוג — הוא לא מתחזה לפריסה שלא קרתה.
3. **הדגמה** — `npm run build:demo` (בונה עם `.env.demo` אל `dist-demo/`), מסנכרן
   ל‑`/home/runner/hadas-demo/html`, מוודא שהקונטיינר רץ, ומושך את הכתובת לבדיקת חיים.
4. **סיכום** — מה קרה בכל יעד.

> **הפריסה של ההדגמה עובדת רק מהשרת שמארח אותה.** הסנכרון הוא העתקת קבצים מקומית.
> מכל מחשב אחר `npm run deploy:vercel` יעבוד, וההדגמה תיכשל בהודעה ברורה.

**עדכון ההדגמה אינו מפיל אותה** — nginx מגיש תיקייה מחוברת (bind mount), אז החלפת
הקבצים היא מיידית ובלי הפעלה מחדש.

### לשנות את סיסמת ההדגמה

```bash
nano .env.demo          # VITE_DEMO_PASSWORD=...
npm run deploy:demo
```

## 7. פתרון תקלות

| תסמין | סיבה סבירה | טיפול |
|---|---|---|
| **503** מהכתובת | Traefik עוד לא קלט את הקונטיינר, או שהוא לא רץ | `sudo docker ps \| grep hadas-demo`; אם חסר — `cd ~/hadas-demo && sudo docker compose up -d`. אחרי הרמה יש להמתין ~30 שניות |
| **404** מהכתובת | תווית ה‑Host ב‑`docker-compose.yml` לא תואמת לדומיין | להשוות את `traefik.http.routers.hadasdemo.rule` לכתובת |
| **מסך לבן** | שגיאת JS — כמעט תמיד `VITE_SUPABASE_URL` ריק בבילד | לוודא ש‑`.env.demo` קיים ומלא, ולבנות מחדש |
| **שינוי לא מופיע** | מטמון של Cloudflare או של הדפדפן | רענון קשיח; אם צריך — Purge Cache בפאנל של Cloudflare |
| **שגיאת תעודה** | Traefik לא הצליח לחדש מול Let's Encrypt | `sudo docker logs coolify-proxy \| grep -i acme` |
| **ההדגמה מציגה מסך התחברות אמיתי** | נבנתה בלי `--mode demo` | `npm run build:demo`, לא `npm run build` |
| **`docker: permission denied` בפריסה** | `runner` אינו בקבוצת docker | הסקריפט נופל אוטומטית ל‑sudo; לתיקון קבוע: `sudo usermod -aG docker $USER` והתחברות מחדש |

## 9. להפריד לריפו נפרד בעתיד

כרגע ההדגמה והמערכת חולקות ריפו אחד. זו החלטה מכוונת: היא מבטיחה שהשתיים לא ייפרדו,
ושתיקון באג מגיע לשתיהן באותה פקודה.

כשתהיה סיבה להפריד (למשל הדגמה עם מיתוג של לקוח אחר), הפירוד זול — כל קוד ההדגמה
מרוכז בקבצים שבטבלה למעלה, ובאפליקציה עצמה נגענו ב‑`App.tsx` בלבד:

1. `git clone` לריפו החדש
2. למחוק את יעד `vercel` מ‑`scripts/deploy.mjs`
3. `npm run deploy:demo` מהריפו החדש

**עד אז — פקודה אחת, שני יעדים, אפס סיכון שההדגמה תפגר.**
