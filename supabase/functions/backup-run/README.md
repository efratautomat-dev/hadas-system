# backup-run — הגיבוי השבועי לדרייב

צילום מלא של כל נתוני המערכת, פעם בשבוע, לתוך Google Drive.
עד לפיצ'ר הזה **לא היה גיבוי בכלל** — כל מה שהעסק יודע חי בעותק אחד, בפרויקט
Supabase אחד.

---

## מה הוא כותב

```
<DRIVE_ROOT_ID>/גיבויים/
└── 2026/
    ├── רבעונים/
    │   └── רבעון 3 2026/          ← העתק של הגיבוי האחרון של הרבעון שנסגר
    ├── ספטמבר/
    │   ├── גיבוי 2026-09-05/
    │   └── גיבוי 2026-09-12/
    └── אוקטובר/
        └── גיבוי 2026-10-03/
            ├── suppliers.json          18 קבצים, אחד לכל טבלה
            ├── invoices.json           כל העמודות, נאמן לשחזור
            ├── …
            ├── גיבוי 2026-10-03.xlsx    גיליון לכל טבלה, לקריאה
            └── _manifest.json          ← מועלה אחרון. ראה "סימן השלמות"
```

**מה לא נשמר, ובכוונה:** `system_logs` (דיאגנוסטיקה, והטבלה היחידה שגדלה בלי
גבול), `ingest_lock` (מנעול רגעי), ו-`backup_runs` עצמה. הסיבות כתובות ב-
`_shared/backup-tables.ts` ומועתקות לתוך `_manifest.json` של כל גיבוי, כדי
שההחרגה תהיה ניתנת לבדיקה מתוך הגיבוי ולא רק מהקוד.

**מה הוא לא יכול להגיע אליו:** `auth.users` (סכימה אחרת, לא חשופה ב-PostgREST —
שחזור יוצר את ההתחברויות מחדש, ו-`allowed_users` נושא את מיפוי התפקידים),
קבצי Storage, וקבצי המסמכים בדרייב (שכבר בדרייב). גם אלה רשומים במניפסט, כדי
ש"צילום מלא" לא ייקרא בטעות כ"הכל".

---

## חמשת הכללים שהפונקציה בנויה סביבם

1. **גיבוי קצר גרוע מאין גיבוי.** PostgREST מחזיר 1,000 שורות לכל היותר, וקריאה
   תמימה של `invoices` מחזירה עשירית מהטבלה ומדווחת הצלחה מושלמת. כל טבלה נקראת
   בעימוד, והעימוד מוכח מול ספירה מדויקת **לפי מפתחות ייחודיים** — לא לפי אורך
   המערך, כי שורה שנכנסת באמצע העימוד מזיזה את החלון, מחזירה שורה אחת פעמיים
   ומפילה אחרת, והאורך נשאר נכון. ראה `_shared/backup-read.ts`.
2. **שום דבר לא מגיע לדרייב לפני שכל הטבלאות נקראו.** כשל קריאה עולה אפס כתיבות.
3. **`_manifest.json` מועלה אחרון — והוא סימן השלמות.** תיקייה בלי מניפסט היא
   ריצה שמתה באמצע ההעלאה, וזה נראה לעין בלי לפתוח כלום.
4. **שורת ה-DB היא הרשומה, לא תשובת ה-HTTP.** `pg_net` קוצב זמן הרבה לפני שדאמפ
   מלא מסתיים, ואף אחד לא ער ב-04:00 בלילה.
5. **כישלון אומר איפה נעצר.** `error_stage` נושא `read:invoices` או `upload`.

## אימות

```bash
npm run check:backup     # מגן השלמות, מול טבלאות שמשקרות בכוונה. לא נוגע במסד
```

הבדיקה הזו מריצה את `readTable` האמיתי מול טבלה פיקטיבית שמוסיפה שורה באמצע
העימוד, מוחקת שורות, מאבדת עמוד, ומשתמשת במפתח מורכב — ומוודאת שהמגן נכשל בקול
במקרים הנכונים ומקבל את המקרים התקינים. **מגן שאף אחד לא ראה נכשל הוא מגן שאף
אחד לא בדק.**

## הפעלה

```bash
# גיבוי רגיל
curl -X POST -H "x-hadas-key: $HADAS_API_KEY" \
  https://<project>.supabase.co/functions/v1/backup-run

# תוכנית וספירות בלבד — לא כותב לדרייב ולא יוצר שורת ריצה
-d '{"dryRun":true}'

# להוכיח את מגן העימוד על מסד קטן: עמוד של 3 שורות
-d '{"dryRun":true,"pageSize":3}'

# להוכיח שהמגן נכשל: עוצר אחרי עמוד אחד
-d '{"pageSize":3,"debugMaxPages":1}'          # מצפים ל-500 + שורה failed + אפס קבצים

# להריץ את ענף הרבעון בלי לחכות שלושה חודשים (בדיקה בלבד)
-d '{"now":"2027-01-03T01:00:00Z"}'

# ניקוי סוף שנה — חייב mode מפורש ו-confirm
-d '{"mode":"year-end-cleanup","year":2026,"confirm":true}'
```

⚠️ **ב-PowerShell אין `curl` אמיתי** — הקריאות נכתבות ב-`Invoke-RestMethod`
(`spec/STATUS.md`, מלכודות חוזרות).

## תזמון

**`supabase/SCHEDULE-DB-BACKUP.sql`** — זה הקובץ שמריצים, ב-SQL Editor של
Supabase. הוא שולף את ה-URL ואת שתי הכותרות חזרה מתוך `cron.job` של
`invoices-ingest-cron`, כך שהמפתח האמיתי לעולם לא מוקלד ולא נכנס לריפו.

שני 01:00 UTC — הלילה שבין ראשון לשני, 03:00–04:00 בישראל (החלטת בעלת העסק 18.10.2026; קודם: שבת). השעה נבחרה גם מפני שאז הקליטה הכי שקטה — ושורה שנכנסת בזמן קריאת
טבלה היא המרוץ היחיד שהמגן חייב להיכשל עליו.

⚠️ **התזמון לא נמצא בשום מיגרציה.** pg_cron מוגדר ידנית, כי אסור לקומיט את
המפתח. זו התבנית הקיימת לשתי משימות הקליטה.

⚠️ **אם המשימה תימחק ולא תיווצר מחדש — שום דבר לא יתריע.** ריצה שלא קרתה לא
יכולה לדווח על עצמה. הפאנל בהגדרות נצבע באדום כשהגיבוי האחרון מלפני יותר מעשרה
ימים, וזה הסימפטום היחיד שקיים לזה.

## סדר פריסה

```
1. supabase db push                              # 20261007000000_backup_runs.sql
2. supabase functions deploy backup-run
3. supabase functions deploy hadas-api           # הראוטים + המודול המשותף
4. supabase functions deploy invoices-ingest     # driveUploadFile עבר ל-_shared
5. לבדוק עם מי משותפת תיקיית השורש בדרייב        # ראה אבטחה, למטה
6. "גיבוי עכשיו" בהגדרות → לפתוח את הדרייב ולהסתכל
7. supabase/SCHEDULE-DB-BACKUP.sql               # רק אחרי ש-6 עבד
```

⚠️ **שלבים 3 ו-4 אינם אופציונליים.** `driveUploadFile` ו-`driveTrashFile` עברו
אל `_shared/drive-filing.ts` ו-`getGoogleAccessToken` אל `_shared/google-auth.ts`.
שתי הפונקציות מייבאות אותם עכשיו; פריסה חלקית תשבור קליטה או מחיקת חשבונית.

## אבטחה — שתי נקודות

**הגיבוי עצמו הוא נכס רגיש.** תיקייה אחת בדרייב שמכילה כל סכום, כל ספק, ואת
`allowed_users`. תיקיות בדרייב **יורשות הרשאות מההורה** — אם `DRIVE_ROOT_ID`
משותפת עם מישהו, כך גם `גיבויים/`, והקובץ שבתוכה מכיל בדיוק את מה ש-`invoices_v`
קיימת כדי להסתיר. **לבדוק את שיתוף תיקיית השורש לפני הריצה הראשונה בפרודקשן**,
ואם היא משותפת — ליצור את `גיבויים` ידנית עם ירושה מנותקת.

**הרשאות בתוך המערכת:** `backup_runs` היא מנהלת-בלבד ב-RLS, ושני הראוטים
(`POST /backups/run`, `POST /backups/year-end-cleanup`) אינם ב-`employeeMayAccess`
ולכן חסומים לעובדת. לפונקציה עצמה אין מסלול JWT בכלל — רק `x-hadas-key`.
